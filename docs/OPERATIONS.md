# 운영 가이드

## 리드 300개 준비 방식

1. `plan`에서 트랙별 검색어를 확인한다. 첫 타깃 묶음은 3개 트랙을 분리한다.
2. 후보를 공식 홈페이지·전시회 명단·채널 파트너 모집 페이지에서 조사한다. 후보 수와 검증 회사 수를 분리한다.
3. 회사명·공식 웹사이트·국가·출처 URL·확인일·짧은 원문·연락처 출처를 기록한다. `examples/company.json`은 형식만 참고하고 실제 사실로 바꾼다.
4. 각 20개 이하의 JSON 파일을 `private/`에 저장한다. 300개는 15번의 import로 누적한다. 도메인 중복은 합치며 같은 연락처가 다른 회사에 연결되면 전체 배치를 중단한다.
5. 증거와 연락처의 ID를 조회하고 확인한 자료만 `verify`한다. 근거는 기본 30일 이내, 원문에 이메일이 정확히 있어야 한다.
6. `cycle`로 초안과 보고서를 만든다. 내용이 검증 전이라면 후보로 남긴다. 수량을 맞추기 위해 검증 값을 채우지 않는다.

## 발송 전 확인할 실제 항목

수신자·회사·제안 트랙·정확한 문안·발신 주소·수신동의 증거를 확인한다. 승인 SHA는 `draft` 출력 및 HTML 리포트에서 확인한다. `dispatch ID`는 dry-run이며 차단 사유만 확인한다. 실제 발송 지시가 있을 때에만 `--live`를 사용한다. 이 코드 생성 요청은 잠재 고객에게 실제 연락할 권한이 아니다.

토큰은 셸 환경이나 운영 secret manager로 주입한다. `.env.example`은 변수 이름 안내일 뿐이며 CLI가 자동 로드하지 않는다. 브라우저 ChatGPT Gmail 연결과 worker credential은 서로 공유되지 않는다. 토큰 갱신은 운영 환경에서 처리하며, 만료 시 발송을 중단한다.

Gmail 프로필 확인에는 `gmail.metadata`, 발송에는 `gmail.send`를 함께 사용할 수 있다. Google OAuth 앱과 해당 API·권한 승인이 먼저 필요하다. 현재 환경에서 Google API 또는 Brave API 접근이 제한되어 있으면 허용된 운영 서버에서 실행한다. 프록시·TLS 보호를 우회하지 않는다.

## 회신과 검색 학습

`examples/reply.json`의 실제 발신자·메일 ID·opportunity/contact ID·회신 시각을 채워 `reply`로 기록한다. outcome은 `positive`, `meeting`, `rfq`, `not_now`, `negative`, `unsubscribe`, `bounce` 중 하나다. 인용된 이전 메일과 현재 회신을 구분해 사람이 분류한다. unsubscribe가 포함되면 다른 결과보다 우선하여 기록한다.

`query_id`는 선택 사항이다. 실제 해당 검색어로 얻은 리드임을 검토자가 확인한 경우에만 넣는다. 넣지 않으면 CRM 상태는 바뀌지만 검색어 성과에는 반영하지 않는다. 출처 인과관계를 자동 추정하지 않는다. 우선순위는 `(positive+1)/(positive+negative+2) + 1/(attempts+1)`로 계산한다. 이것은 작은 표본의 탐색·활용 휴리스틱이며 실제 전환율·매출 예측이 아니다.

수신거부·반송·부정 회신은 전역 suppression으로 기록한다. 회신이 있으면 해당 수신자의 초안은 추가 발송되지 않는다. `not_now`도 자동 재접촉을 예약하지 않는다. 명시적 후속 요청은 별도 검토가 필요하다.

## 상태 복구

- `UNKNOWN`: Gmail API 응답이 모호한 상태. 동일 수신자 예약을 제거하지 말고 Gmail Sent/고정 Message-ID를 먼저 확인한다.
- `SENDING`: 프로세스가 예약 후 중단되었을 수 있다. 미전송이라고 단정하거나 예약을 삭제하지 않는다.
- `ACCEPTED`: Gmail이 메시지 ID를 반환했다. 고객 도착·열람은 측정하지 않았다.
- 검색 실패: queries.next_at을 기다린 후 다시 유한 사이클을 실행한다. 429/403 등 상세 점검은 운영 계정에서 하며 로그에 토큰을 남기지 않는다.

현재 UNKNOWN/SENDING 재조정 CLI는 제공하지 않는다. 근거를 확인한 운영자가 DB 백업 후 감사 기록과 함께 수동 처리해야 한다. 편리함을 위해 무조건 재발송하는 기능은 추가하지 않는다.

## 저장소와 백업

운영 서버에서 DB 경로는 영속 볼륨으로 지정한다. 접근권한을 운영자에게 제한한다. 로컬 기본 DB는 개발 확인용이며 클라우드 scratch의 장기 보존을 보장하지 않는다. 배포 산출물에 DB·private·보고서·환경파일을 포함하지 않는다. CI는 mock/메모리 DB만 사용하고 실발송 credentials를 등록할 필요가 없다.
